## Review Focus

Nothing in the slice specs pins these failure modes. The tests for the first three go in Task 4
(only `tests/s22_pty_sixel_thread.rs` may gain new test names). The last two are read-checks for
the Task 4 reviewer.

1. **Fast hovering across several wallpapers:** `j`/`k` while encodes are in flight must end with the hovered wallpaper drawn, not blank forever (tested). A response must never be drawn on the wrong picture (read-check: replies are routed by `(path, serial)`, never by trying every entry).
2. **`q` while an encode is pending:** it exits 0 within 1 s on the first press, with no wait for the worker.
3. **`LN_HUB_TIMING` points at a path that cannot be opened:** the app runs normally and logs nothing. No crash, no stderr noise in the TUI. (My call: timing is silently off.)
4. **The query result arrives while an encode is in flight:** `cache.clear()` re-creates entries. The old response carries an old serial and is dropped. It must never be applied to the new entry for the same path. (Read-check: serials come from one counter per `ImageView`, not per path.)
5. **`ESC P` split across two writes:** the draw-time detector must still see it (read-check: the spy keeps the "last byte was ESC" state between `write` calls).

### Task 4: S22 sixel encode off the UI thread + `LN_HUB_TIMING`

**Slice spec** (binding; folded in from the former `tasks/ln-hub-v1/s22-sixel-off-ui-thread.md`):

- slice_id: S22-sixel-off-ui-thread
- behavior:
  1. The sixel resize+encode runs on a worker thread through `ratatui_image::thread::ThreadProtocol`
     (ratatui-image 11.1, no extra feature flag; the `thread` module is not feature-gated and the
     `tokio` feature stays off). The UI thread never calls `resize_encode`. While an encode is
     pending, keys are handled and the rest of the UI redraws. When the response arrives, the
     `main.rs` loop applies it with `update_resized_protocol` and redraws. A stale response is
     dropped. The path-keyed cache (`CACHE_CAP = 8`) stores `ThreadProtocol` entries.
  2. Opt-in timing log. When the env var `LN_HUB_TIMING=<file>` is set, the bin appends to
     `<file>`:
     - `encode <cols>x<rows> <ms>ms`, one line per finished encode, written by the worker;
     - `draw <ms>ms`, one line per frame that emitted sixel bytes, timing the `terminal.draw`
       call that flushed them.

     `<ms>` has exactly one decimal (`12.3`), so the line matches `^encode \d+x\d+ \d+\.\dms$` /
     `^draw \d+\.\dms$` (the VM check, S24, parses these). Nothing is written, and the file is not
     created, when the env var is unset. This lets the VM check tell encode cost from terminal
     write cost.
- seam: the public seam is unchanged: all changes are in the bin (`src/image_view.rs`,
  `src/main.rs`); nothing in `src/lib.rs` or the `App` API moves. `LN_HUB_TIMING` is bin-only and
  is not part of the lib seam. Verified by a pty test of the real binary (and manually in the VM,
  S24).
- depends_on: S21-pty-helper-dedup (uses `Session::fail` and the shared helpers), S20 (the
  `cargo fmt --check` criterion).
- test_paths: [tests/s22_pty_sixel_thread.rs, tests/common/pty.rs]

  - GREEN: the new test passes and the full suite is green; `cargo clippy --all-targets -- -D

  - The reviewer confirms by reading: no call to `resize_encode` and no `StatefulProtocol` render
    path (`render_stateful_widget` on a `StatefulProtocol`) remains on the UI thread;
    `ThreadProtocol` is the only protocol type stored in the cache; `grep -n "StatefulProtocol"
    src/image_view.rs` shows it only where the worker-side or construction code needs it.
  - With `LN_HUB_TIMING` unset, `grep`/read confirms no timing file is opened and no timing
    wrapper cost is paid per frame beyond one `Option` check.
  - The manual VM check (responsiveness and the real encode/draw numbers) is S24.
- Decisions:
  - Why a test that only reads a log is an acceptable RED: the interface that is new and
    observable from outside is the timing log, so the test fails today for the right reason (no
    `encode ` line). The responsiveness claim itself ("a key is handled while an encode is
    pending") cannot be pinned by a pty test without a race: before S22 a `?` sent right after
    `l` is also handled, because the decode (already off-thread) has not finished yet. It is
    asserted weakly here (help line appears) and measured for real in S24. Said in the test's
    comment.
  - `ThreadProtocol` is opaque (verified in ratatui-image 11.1.0, `src/thread.rs`):
    `ResizeRequest` / `ResizeResponse` expose nothing but `resize_encode()`, each
    `ThreadProtocol` keeps its own id starting at 0 (so ids collide across the 8 cache entries),
    and the request carries no path or size. So:
    - A response must be routed to its entry by a tag the bin adds, never by trying
      `update_resized_protocol` on every entry (a colliding id would mis-apply the response to
      the wrong picture; that is a real bug, not only a stale drop). The tag is the path plus a
      per-entry serial, so a response whose entry was evicted, or evicted and re-created for the
      same path (a fresh `ThreadProtocol` restarts at id 0), is dropped.
    - `<cols>x<rows>` in the log cannot be read from the request. The bin records the size it
      asked for when the request is made (the size `needs_resize` returned for the preview area).
    - One viable shape: each cache entry owns an `mpsc::Sender<ResizeRequest>` whose receiving
      end is drained into one shared worker as `(path, serial, size, request)`; the worker calls
      `request.resize_encode()`, times it, appends the `encode` line, and sends
      `(path, serial, response)` back; `ImageView::poll` applies it with
      `update_resized_protocol`. The shape is the implementer's call as long as the routing and
      tagging rules above hold. Requests are forwarded promptly (not only once per loop
      iteration, whose `event::poll` can sleep up to 100 ms).
  - A failed encode (`resize_encode` returns `Err`) leaves the entry's protocol consumed. The
    entry becomes `Failed` (blank, not retried), never pending forever.
  - Decided (user, 2026-11-07): the preview is BLANK while an encode is pending. Background: the brief said the preview "keeps the previous image if there is one; otherwise
    blank". The stock `ThreadProtocol::resize_encode` takes its inner protocol for the whole
    encode, and a `ThreadProtocol` without an inner renders nothing, so the area is BLANK while
    an encode is pending, also when the same image is being re-encoded after a resize of the
    terminal. Keeping the old picture would need `ImageView` to hold and render the last ready
    protocol itself (a custom widget), which this slice does not add. The slice therefore
    guarantees input and redraw (not the old picture) and S24 records by eye what the area
    shows while pending. Keeping the old picture was offered and declined.
  - The decode worker and the `Decoded` flow stay as they are. The first frame after a decode is
    a `ThreadProtocol` whose inner is the fresh `StatefulProtocol`, which `StatefulImage` sends
    for its first `resize_encode`.
  - The timing is taken in the bin only. `draw <ms>ms` needs to know a frame emitted sixel
    bytes; one way is a wrapper around the terminal's stdout writer that notes an `ESC P` in what
    passes through and times the `draw` call; the implementer may choose another way. It must
    time the call that flushed the bytes, because the write to the terminal can block when the
    terminal is slow (the thing S24 wants to separate from the encode).

**Algorithm decisions the signatures don't fix:**
- **`ImageView::render`, for a `Ready` entry:**
  - First get `let size = ready.proto.needs_resize(&resize, preview.area.into())`.
  - Then call `render_stateful_widget(StatefulImage::default().resize(resize), ..)` on `ready.proto`.
  - Then, in the same call, `try_recv` every request on `ready.requests` and send `EncodeJob { path, serial, size, request }` to the worker. `size` falls back to `preview.area.into()` if `needs_resize` gave `None`.
  - This forwards requests within the frame, not once per loop iteration.
- **Encode worker:** one thread. For each job it times `request.resize_encode()` inside `panic::catch_unwind`, treating a panic as `Err`. When timing is on it logs `encode {w}x{h} {fmt_ms}` for every finished encode, `Ok` or `Err` (my call). Then it replies with `Encoded`, where `Err` or a panic becomes `response: None`.
- **`ImageView::poll`:** drain `Encoded` and decrement the in-flight count.
  - Find the entry whose path matches, is `Ready`, and has the same `serial`. If there is none, drop the reply. That covers eviction, re-creation and the query `cache.clear()`.
  - `Some(resp)` goes to `proto.update_resized_protocol(resp)`.
  - `None` turns the entry into `Entry::Failed`.
- **Terminal setup in `main`:**
  - `let _ = ratatui::init();` installs ratatui's panic hook, raw mode and alternate screen; drop the `DefaultTerminal` it returns.
  - Then build `Terminal::new(CrosstermBackend::new(BufWriter::new(SixelSpy { inner: io::stdout(), seen: seen.clone(), last_was_esc: false })))`.
  - `seen` is `Some(Arc<AtomicBool>)` only when `timing.is_some()`.
  - `ratatui::restore()` stays as the teardown.
- **Draw timing in `run`:** `let t = Instant::now(); terminal.draw(..)?;`. If `seen` is `Some` and `swap(false)` returns true, log `draw {fmt_ms(t.elapsed())}`. `Terminal::draw` flushes, so this covers the terminal write.
- **Loop wait:** `event::poll(if images.encode_pending() { 10 ms } else { 100 ms })` (my call). A finished encode is then drawn within about 10 ms instead of up to 100 ms.
- **Preview while pending:** blank, also on a terminal resize. The user decided this on 2026-11-07, and it is recorded in the slice spec.
